**dhcp-snooping-82 0.2.0** adds IPv6: a DHCPv6 Lightweight Relay Agent (RFC 6221), the IPv6 counterpart of Option 82, with prefix delegation, DHCPv6 snooping and an RA guard. It remains a drop-in replacement for the airOS `/bin/dhcp-fwd`.

Tested on two production stations with airOS WA.v8.7.11 and WA.v8.7.12 (PowerBeam 5AC, Station WDS, kernel 2.6.32). On the IPv6 sector a MikroTik DHCPv6 server delegated the customer's /57 through the agent on the first attempt; its binding shows our relay chain (peer = customer router, link-address `::`, Interface-ID `<hostname>/br1:eth0`). The binary in this release runs on both stations.

## New

- **DHCPv6 lightweight relay agent (RFC 6221).** Client messages from untrusted ports (Solicit, Request, Renew, Rebind, Release, Decline, Confirm, Information-Request) are wrapped into a Relay-Forward with
  - Interface-ID (option 18), by default the same text as the circuit ID, e.g. `station-01/br1:eth0`,
  - Remote-ID (option 37), enterprise number 41112 + bridge MAC,
  - link-address `::`, peer-address = the client.

  MAC and IP addresses stay the client's, the message goes out exactly once on the uplink. A Relay-Reply with our Interface-ID is unwrapped and delivered as a plain server message to port 546, only on the port the Interface-ID names.
- **Prefix delegation:** IA_PD passes unchanged inside the relay messages, so PD works through the upstream relay. Rapid commit works as well.
- **DHCPv6 snooping:** Relay-Forward and server messages (Advertise, Reply, Reconfigure, Relay-Reply) from customer ports are dropped (RFC 6221: customer ports are untrusted), as are other customers' DHCPv6 messages and Relay-Replies for other relays arriving from the uplink.
- **RA guard:** router advertisements from customer ports are dropped, also when hidden behind hop-by-hop or destination options headers (RFC 7113), and fragmented neighbour discovery is dropped (RFC 6980). The ebtables of kernel 2.6.32 cannot match ICMPv6 types, so all link-local ICMPv6 of a customer port goes through the agent, which passes everything except RAs on unchanged.
- **Command line:** `dhcpv6.snooping=yes|no` and `dhcpv6.RAguard=yes|no` (both on by default); any `SECTION.KEY=VALUE` now works without `-o`. Further keys: `dhcpv6.interface_id`, `dhcpv6.remote_id`, `dhcpv6.enterprise`, `dhcpv6.unicast=relay|forward`.
- `--diag` also shows DHCPv6, `--check` the IPv6 settings and IDs, the stats file has IPv6 counters.

## Upgrade from 0.1.0

```sh
# on the PC
sha256sum -c SHA256SUMS
tar xzf dhcp-snooping-82-0.2.0-mips.tar.gz
cd dhcp-snooping-82-0.2.0
scp -O dhcp-fwd dhcp-snooping-82.sh dhcp-snooping-82.conf root@DEVICE:/tmp/

# on the device
sh /tmp/dhcp-snooping-82.sh install                          # keeps your configuration
/etc/persistent/dhcp-snooping-82/dhcp-snooping-82.sh activate  # mounts the new binary, restarts the agent
sh /etc/persistent/dhcp-snooping-82/dhcp-snooping-82.sh install --save
```

The agent is off for a few seconds while it restarts. A fresh installation works as described in the README and the 0.1.0 notes.

## Things to know

- The upstream relay or DHCPv6 server must accept Relay-Forwards from a lightweight relay (link-address `::`) and echo the Interface-ID, as RFC 6221 requires. The MikroTik DHCPv6 server does.
- Without IPv6 on a sector nothing changes for the customer; DHCPv6 and RA guard simply see no traffic. Use `dhcpv6.snooping=no` / `dhcpv6.RAguard=no` to switch them off.
- With the RA guard on, the station itself no longer receives multicast neighbour discovery from the customer side, so it cannot be reached over IPv6 from the customer's LAN. From the uplink side nothing changes.
- If the worker crashes, link-local ICMPv6 of the customer is blocked until it is back (fail-closed), so IPv6 pauses for a few seconds.
- Known limitations of 0.1.0 still apply: standard firmware runs no boot hook (call `ensure` after a reboot, or use CS firmware), and airOS flushes ebtables on every "Apply" (rules are back within 5 seconds).
